1. The problem worth solving

Analysts build Streamlit dashboards. The dashboards break. The data engineering team gets the ticket, having never seen the code, never reviewed the query, and never agreed to support it.

The instinct is to restrict who can build apps. That is the wrong diagnosis — self-service is working, and that is the point. The real failure is that there is no defensible line between a dashboard someone assembled in an afternoon and a dashboard the business now depends on, so every app defaults to being the platform team's problem.

A line drawn with naming conventions or a spreadsheet of "official" apps does not hold. It depends on people remembering to update it, and it is unfalsifiable — anyone can claim their app matters.

2. The governance signal

Snowflake records where an app's code came from, on the app object itself, written by the deployment mechanism rather than by a person. 

DESCRIBE STREAMLIT CORTEX_AGENTS_DEMO.PUBLIC.CORTEX_AGENT_CHAT_APP;
default_version_source_location_uri  @...GITHUB_REPO_CORTEX_AGENTS_DEMO/branches/main/agent_app/
default_version_git_commit_hash      15e3e34e80cdc1e8d64b34a1d0b8ad206d002c1b

That is a real value from a live app. Its running code traces to a specific commit on a specific branch — you can open that commit and read the diff that produced what users see right now. Nobody typed the hash in, and an app that did not come from a repository cannot produce one.

The trap: there are two governed paths, recorded differently

This is the part most people get wrong, and getting it wrong misclassifies your best apps as ungoverned.

Pathsource_location_urigit_commit_hashWhere the evidence lives
CREATE STREAMLIT FROM @git_repo/…Git stage pathpopulatedThe app object
DCM DEFINE STREAMLIT FROM 'asset://…'asset://<name>emptySHOW DEPLOYMENTS IN DCM PROJECT
Clicked together in Snowsightinternal stageemptynowhere

A DCM-deployed app has no commit hash on the object, yet it is the most governed kind of app in the estate: reviewed, CI/CD-deployed, reproducible. An audit keyed only on the hash reports it as ungoverned. Accept either form of evidence.

3. What an audit finds

There is no ACCOUNT_USAGE view for Streamlit, so an inventory has to loop SHOW STREAMLITS plus DESCRIBE STREAMLIT into a table. Run against a real account of 81 apps, that produced:

81

79

60

Three of these change how you plan:

  • 79 of 81 have no provenance. When one breaks there is no diff to read and no commit to roll back to. That is the support-load problem in one number.
  • 60 of 81 use the legacy ROOT_LOCATION source model. Those apps cannot use Git integration or the container runtime at all. This is a hard technical ceiling, not a process gap — three quarters of the estate must be migrated to FROM before a Git workflow applies to them. Any plan that says "start using Git" understates the work by that number.
  • 81 of 81 have no exact version pin. Range pins silently do not take effect, so every app can change behaviour with no code edit.
Reproduce it on your own account
snow sql -f audit/streamlit_inventory.sql
snow sql -q "CALL GOVERNANCE.APPS.SP_AUDIT_STREAMLIT_APPS()"
snow sql -q "SELECT * FROM GOVERNANCE.APPS.V_STREAMLIT_SPRAWL_SUMMARY"

Why this works
The tier is derived from a property of the object, not from an opinion. When a Tier 1 app breaks, the conversation is a query rather than a negotiation — and the route to getting support is visible and self-service: put it in Git, open a PR. That reframes the platform team from gatekeeper to provider of a promotion path.

5. Project structure

Keep streamlit_app.py about layout and move queries into modules, so session-state behaviour stays easy to reason about.

demo_app/
├── manifest.yml                  # DCM targets, assets, templating
├── sources/definitions/
│   ├── pipeline.sql              # DEFINE TABLE / VIEW
│   ├── access.sql                # DEFINE ROLE + GRANT
│   └── dashboard.sql             # DEFINE STREAMLIT
└── streamlit/merch_performance/
    ├── streamlit_app.py          # entry point — UI only
    ├── requirements.txt          # exact pins
    └── utils/
        ├── config.py             # runtime env inference
        └── data.py               # parameterized queries
  • Entry point is always streamlit_app.py.
  • No if __name__ == "__main__" — Streamlit re-runs the whole file on every interaction.
  • .github/workflows/ must be at the repository root. Actions does not discover workflows in subdirectories.
  • Never commit .streamlit/secrets.toml.

6. Owner's rights vs caller's rights

This is the most important architectural decision, because it determines whose permissions the app uses. A Streamlit app runs with the privileges of its owner role — every viewer reaches data through them.

AspectOwner's rights (default)Caller's rights
Runs asThe creator's roleThe viewer's role
Data seenSame for all viewersOnly what each viewer's role permits
CURRENT_ROLE()The owner's roleThe viewer's role
Row access policies segment viewersnoyes
Viewer data grantsNot neededRequired for every viewer
RuntimeEitherContainer only
Best forDashboards and reporting — most appsPer-user data segmentation
80% of audited apps are owned by an admin role
65 of 81 apps are owned by ACCOUNTADMIN, SYSADMIN, or SECURITYADMIN. Each hands admin-level reach to everyone who can open the dashboard. This is the highest-severity finding in the estate, ahead of the provenance gap — and because Streamlit ownership cannot be transferred, those apps must be recreated under a functional role, not re-granted.

The self-service unblock

Non-admin users being unable to create apps is a real blocker with a small fix:

GRANT USAGE ON DATABASE APP_DB              TO ROLE SIS_DEVELOPER;
GRANT USAGE ON SCHEMA APP_DB.APPS           TO ROLE SIS_DEVELOPER;
GRANT CREATE STREAMLIT ON SCHEMA APP_DB.APPS TO ROLE SIS_DEVELOPER;
GRANT USAGE ON WAREHOUSE APP_WH             TO ROLE SIS_DEVELOPER;
-- container runtime only
GRANT USAGE ON COMPUTE POOL APP_POOL        TO ROLE SIS_DEVELOPER;
Two grants people ask for and usually do not need

CREATE STAGE is required only for the legacy ROOT_LOCATION pattern. On the FROM model the app uses an embedded stage, so if users are blocked on stage creation, migrating removes the blocker rather than needing a new privilege.

CREATE STREAM is required only if the app itself operates on streams. Check whether that is genuinely the case — the requirement is often inherited from the legacy pattern. This is a chance to remove a privilege instead of adding one.

7. Git integration

Check the source model first — only one of the two can use Git at all:

DESCRIBE STREAMLIT <db>.<schema>.<app>;
-- returns root_location              -> LEGACY, cannot use Git
-- returns live_version_location_uri  -> current, Git-capable

Public repository — no credentials

CREATE OR REPLACE API INTEGRATION GIT_API_MY_ORG
  API_PROVIDER = git_https_api
  API_ALLOWED_PREFIXES = ('https://github.com/my-org')
  ENABLED = TRUE;

CREATE OR REPLACE GIT REPOSITORY MY_DB.MY_SCHEMA.MY_REPO
  API_INTEGRATION = GIT_API_MY_ORG
  ORIGIN = 'https://github.com/my-org/my-repo';

ALTER GIT REPOSITORY MY_DB.MY_SCHEMA.MY_REPO FETCH;

Private repository — read-only secret

CREATE OR REPLACE SECRET MY_DB.MY_SCHEMA.GIT_PAT
  TYPE = PASSWORD
  USERNAME = 'my-github-user'
  PASSWORD = '<fine-grained PAT, Contents: Read>';

Then add ALLOWED_AUTHENTICATION_SECRETS to the integration and GIT_CREDENTIALS to the repository. Snowflake only ever fetches — never grant write scope.

SSO gotcha
If the repository is in an organization with SAML SSO enforced, a classic PAT must be explicitly authorized for that organization (Configure SSO → Authorize) or the fetch fails with an opaque not-found error indistinguishable from a wrong URL. Fine-grained tokens scoped to the repository avoid this.

Deploying straight from Git is what puts the commit hash on the object. Use a tag for production — a branch moves, a tag is what you can roll back to.

CREATE OR REPLACE STREAMLIT MY_DB.SERVE.MY_APP
  FROM @MY_DB.MY_SCHEMA.MY_REPO/branches/main/apps/my_app/
  MAIN_FILE = 'streamlit_app.py'
  QUERY_WAREHOUSE = MY_WH;

8. Promotion with DCM Projects

A dashboard is the visible part of something larger: the tables it reads, the view that defines its contract, the roles that decide who sees what. Promoting only the Python file is how you get a PROD app pointed at a DEV table. DCM Projects make the app, its data, and its access model one deployable unit. 

snow dcm plan   --target prod --save-output
snow dcm deploy --target prod --alias "$(git rev-parse --short HEAD)"
DCM Jinja variables do not reach your Python files

You can template the DEFINE STREAMLIT statement. You cannot template the app source. The tempting shortcut is fatal:

# WRONG — deploys happily to PROD, silently reads DEV data
DATABASE = "FANATICS_MERCH_DEV"

Nothing errors. The dashboard renders. The numbers are just wrong, which is worse than a failure. Ask Snowflake at runtime instead:

database = conn.query("SELECT CURRENT_DATABASE() AS DB", ttl=3600)["DB"].iloc[0]
Asset globs: deploys cleanly, fails at runtime

The literal directory prefix before the first wildcard is stripped when files are materialized. For an app with a utils/ package:

Manifest entryutils/config.py becomesResult
'app/utils/config.py'config.pyimports break
'app/utils/*.py'config.pyimports break
'app/**/*'utils/config.pycorrect

So any app with a subpackage requires the ** form. The cost is that ** sweeps in __pycache__, which DCM does not exclude — set PYTHONDONTWRITEBYTECODE=1 and clean before deploying. Always verify with find out/rendered/assets -type f.

9. CI/CD

Two corrections to the February guide

Authentication. That guide stored a password as SNOWCLI_PW. Snowflake's CI/CD guidance says password authentication is supported for legacy workflows but is not recommended for production. Use key-pair, or OIDC workload identity federation to remove the stored secret entirely.

Never bare --replace. snow streamlit deploy --replace is a create-or-replace that can drop the grants on the app — silently revoking business users' access to a production dashboard. DCM reconciles the object and keeps grants declared alongside it. 

- name: Clean stray bytecode
  run: find . -name '__pycache__' -type d -prune -exec rm -rf {} + || true

- name: DCM plan
  env:
    SNOWFLAKE_AUTHENTICATOR: SNOWFLAKE_JWT           # key-pair, not a password
    SNOWFLAKE_PRIVATE_KEY_PATH: ~/.snowflake/rsa_key.p8
    PYTHONDONTWRITEBYTECODE: '1'
  run: snow dcm plan --target dev --save-output

Put required reviewers on the GitHub Environment, not in workflow logic — environment protection cannot be bypassed by editing the workflow in the same PR. Then verify provenance landed, and fail the build if it did not, so the catalog stays honest.

10. Dependency pinning

Pin exact versions. Never ranges.
Range pins such as streamlit>=1.39.0 do not reliably take effect on the warehouse runtime (SNOW-3601653). The app runs on whatever the runtime picks, and that can change with no code edit and no deployment. 81 of 81 audited apps have no exact pin. This is not hypothetical — the filter-state bug investigated in September reproduced on deployed SiS but not on local Streamlit 1.50, because the deployed version was not what the developer assumed.
RuntimeDependency fileNotes
Warehouseenvironment.ymlAnaconda channel; supported list tops out at 1.52.2
Containerrequirements.txt / pyproject.tomlPyPI; required for caller's rights and non-Anaconda packages
Two measured traps

DEFINE STREAMLIT defaults to the container runtime. Omitting COMPUTE_POOL and RUNTIME_NAME still produced a container-runtime app — which silently invalidated a shipped environment.yml, since that is the warehouse format. The file was present, correct, committed, reviewed, and had no effect. Declare the runtime explicitly.

user_packages cannot verify container-runtime pins. It is populated for warehouse-runtime apps but comes back empty for container-runtime apps even with a correct requirements.txt — reading it would tell you the pin failed when it had not. Report the resolved version from inside the app instead: 

st.caption(f"Streamlit runtime: `{st.__version__}`")

11. Session state: four rules

These come from the September filter-state investigation, where a deselected filter reappeared after switching grids. Each maps to a failure observed on a deployed app.

Rule 1 — seed defaults once, before any widget

FILTER_DEFAULTS = {"flt_leagues": [], "flt_channels": []}
for key, default in FILTER_DEFAULTS.items():
    st.session_state.setdefault(key, list(default) if isinstance(default, list) else default)

Rule 2 — a keyed widget passes no index= / value= / default=

st.multiselect("League", options=leagues, key="flt_leagues")                  # correct
st.multiselect("League", options=leagues, default=[], key="flt_leagues")     # wrong

With a key, session_state is the source of truth and the literal is only an initial default. Supplying both makes them compete.

Rule 3 — resets are on_click callbacks, never "pending flag + st.rerun()"

def _clear_filters():
    for k, v in FILTER_DEFAULTS.items():
        st.session_state[k] = list(v) if isinstance(v, list) else v

st.button("Clear filters", on_click=_clear_filters)

Callbacks run before the script re-executes, so widgets rebuild from the reset value. A mid-script st.rerun() truncates the run before later widgets re-register.

Rule 4 — never assign to a widget-bound key after that widget has rendered

Current Streamlit raises StreamlitAPIException. Older deployed runtimes instead produce a stale value that reappears on the next unrelated rerun — much harder to diagnose, and exactly what happened. Snowflake Support case 01322560 classifies this as expected Streamlit execution semantics, not a platform defect.

Each of these was reproduced empirically, not taken from documentation.

13. Sharing apps

Do not share apps by emailing .py files
Recipients lack the creator's secrets, roles, and connection context, so the app fails immediately. Deploy it and share by role grant. 
GRANT USAGE ON STREAMLIT analytics_db.dashboards.my_app TO ROLE analyst_role;

-- so certified apps become visible as they are added
GRANT USAGE ON FUTURE STREAMLITS IN SCHEMA analytics_db.dashboards TO ROLE analyst_role;

Viewers need USAGE on the database, schema, and Streamlit object — and under owner's rights, no grants on the underlying data at all. That is the main ergonomic benefit and why owner's rights is the right default for reporting.
